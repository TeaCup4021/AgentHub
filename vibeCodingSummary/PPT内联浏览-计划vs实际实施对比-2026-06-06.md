> 日期：2026-06-05 ~ 2026-06-06 | 状态：已完成

---

## Plan v1 vs Plan v2 vs 实际实施

### Plan v1：Office Web Viewer 纯前端方案

`AgentHub-PPT内联浏览-实施计划.md` 推荐**方案 A**：PPTX 传给微软 Office Web Viewer（`view.officeapps.live.com`）iframe 预览，方案 C（Gotenberg）为远期备选。

**实际实施：完全未采用**。理由：
- Office Web Viewer 要求文件 URL 公网可达，本地 MinIO 内部文件无法使用
- Gotenberg 方案（方案 C）的代码在当时已经基本就绪

### Plan v2：Gotenberg 后端转换 + 上传路径补全

`AgentHub-PPT内联浏览-实施计划-v2.md` 规划了 4 个步骤：
1. `upload` 端点增加 PPTX→PDF 转换
2. `convert_bytes_sync` 提取到 `converter.py`
3. DocumentCard pptx 分支改为 iframe
4. 类型定义同步

**实际实施**：Plan v2 的 4 个步骤**全部完成**，但发现了 4 个额外的阻塞性 bug 和 1 个新功能需求，共 **9 项改动**。

## 从 6.5 代码到现在的完整变更

### 架构：两条 PPTX 来源 → 一条转换管线

```
PPTX 来源
    │
    ├─ 路径 A：用户上传 (ChatInput 拖拽)
    │   ① POST /api/v1/files/upload
    │   ② upload 端点即时转换 → MinIO (conversions/{id}.pdf)
    │   ③ 前端 ChatArea 拼 prompt: "[附件文件链接]\n{fileUrl}"
    │   ④ SSE → Agent 回复 → message_end
    │   ⑤ _detect_urls → _resolve_internal_file → _maybe_convert_pptx
    │
    ├─ 路径 B：Agent 消息中的 URL (LLM 或 CLI 生成)
    │   ① _detect_urls → 检测到文档 URL → artifact 构建
    │   ② _maybe_convert_pptx → Gotenberg → PDF → MinIO
    │
    ├─ 路径 C：CLI Agent 本地生成文件
    │   ① Claude Code CLI 生成 demo.pptx (cli-workspace/)
    │   ② _emit_cli_generated_file_artifacts 扫描新文件
    │   ③ 上传 MinIO → _maybe_convert_pptx → PDF
    │
    ▼
统一的 DocumentCard 预览:
  fileType=pdf → <iframe src={fileUrl} />
  Content-Disposition: inline  (files.py 修复)
```

## 实施过程中发现的 4 个阻塞性 Bug

| # | 症状 | 根因 | 修复 | Plan v2 预见了？ |
|---|------|------|------|:---:|
| 1 | Gotenberg 502 Bad Gateway | `httpx` 走 Windows 系统代理，localhost 被路由到代理 | 所有 httpx 客户端加 `trust_env=False` | ❌ |
| 2 | Gotenberg 400 no form file | 传给 Gotenberg 的文件名无扩展名，LibreOffice 无法识别格式 | `_resolve_internal_file` 根据 content_type 加 `.pptx` 等后缀 | ❌ |
| 3 | PDF 转换成功但浏览器不渲染 | `Content-Disposition: attachment` 强制下载 | 对 PDF/图片设 `inline` | ❌ |
| 4 | uvicorn reload 反复打断 CLI Agent | CLI 在 backend/ 目录创建文件触发文件监听；`pip install python-pptx` 改动 venv/ 触发重载 | workspace 移出 backend + `--reload-exclude "venv/*"` | ❌ |
