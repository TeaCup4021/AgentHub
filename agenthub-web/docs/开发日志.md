## 2026-05-24

### 问题 2：消息顺序反转 —— 新消息显示在旧消息上方

**现象**

发送第二条消息后，新消息出现在第一条消息的上方，而不是按正常聊天习惯出现在下方。

**根因**

Phase 4.6 对齐后端 cursor 分页时，mock handler 将消息按 `createdAt DESC`（最新在前）排序，但 ChatArea 的 `useMemo` 展平分页数据后直接渲染，没有反转顺序。

后端 cursor 分页标准行为是按 `created_at DESC` 返回（最新消息在前），前端负责在渲染前反转为 ASC（最旧在上、最新在下）。

**解决**

在 `ChatArea.tsx` 的 `useMemo` 展平后加 `.reverse()`：

```tsx
// ✅ 正确：反转 API 的 DESC 顺序为 UI 的 ASC 顺序
const rawMessages = useMemo(
  () => messagesData?.pages.flatMap((p) => p.items).reverse() ?? [],
  [messagesData],
);
```

**原则**

- 后端 API 的排序约定（DESC/ASC）和前端 UI 的展示顺序是两个独立关注点
- cursor 分页天然用 DESC（向后翻页），前端负责反转为 ASC 展示
- 流式新消息出现在底部，历史消息在顶部可滚动加载，这两者互不冲突

### 问题 3：乐观更新消息插入位置错误 —— 新消息跳到顶部且后续消息不显示

**现象**

1. 发送第二条消息后，乐观消息闪烁到列表顶部（第一条消息上方），然后跳回底部
2. 发送第三条消息后，乐观更新完全看不到，仍然等 AI 回复完才出现

**根因**

乐观消息插入到了 DESC 数组的**末尾**而非**开头**。

数据流：
```
Mock handler 返回 DESC 排序:          items = [ai-msg(newest), user-msg(oldest)]
乐观更新 append 到末尾 (BROKEN):      items = [ai-msg, user-msg, optimistic]
reverse() 反转后:                     [optimistic, user-msg, ai-msg]
                                      ↑ 乐观消息跑到了最上面！

正确方式 prepend 到开头:              items = [optimistic, ai-msg, user-msg]
reverse() 反转后:                     [user-msg, ai-msg, optimistic]
                                      ↑ 乐观消息在最下面 ✅
```

后续消息之所以"看不到"，是因为乐观消息出现在了列表顶部（而非底部），用户视线在底部输入框附近，看不到顶部的新消息。

**解决**

[ChatArea.tsx:71](src/components/layout/ChatArea.tsx#L71) 一行改动：

```diff
- items: [...page.items, optimisticMsg]   // append → 跑到 oldest 位置
+ items: [optimisticMsg, ...page.items]   // prepend → 在 newest 位置
```

**原则**

- 理解数据的排序方向：API 返回 DESC（最新在前），前端 `.reverse()` 为 ASC 展示
- 乐观插入必须在"最新"位置（DESC 的开头 = index 0），反转后才在底部
- 不要假设数组末尾就是最新的

## 2026-05-21

### 问题 1：React 无限重渲染 (Maximum update depth exceeded)

**现象**

浏览器控制台报错：
```
Uncaught Error: Maximum update depth exceeded. This can happen when a component
repeatedly calls setState inside componentWillUpdate or componentDidUpdate.
```

同时控制台出现：
```
The result of getSnapshot should be cached to avoid an infinite loop
```

**根因**

在 Zustand 的 `useChatStore` selector 中调用了 store 方法 `s.filteredConversations()`：

```tsx
// ❌ 错误写法
const conversations = useChatStore((s) => s.filteredConversations());
```

`filteredConversations()` 每次调用返回一个新的数组引用。Zustand 使用 `Object.is` 比较 selector 返回值，新旧数组引用不同 → 触发组件重渲染 → 再次执行 selector → 又产生新数组 → 无限循环。

**解决**

只订阅原始数据（`conversations` 数组、`searchQuery` 字符串），在组件内用 `useMemo` 做过滤：

```tsx
// ✅ 正确写法
const rawConversations = useChatStore((s) => s.conversations);
const searchQuery = useChatStore((s) => s.searchQuery);

const conversations = useMemo(() => {
  const q = searchQuery.toLowerCase();
  return rawConversations
    .filter((c) => !c.isArchived && (!q || c.title.toLowerCase().includes(q)))
    .sort((a, b) => {
      if (a.isPinned !== b.isPinned) return a.isPinned ? -1 : 1;
      return new Date(b.lastActiveAt).getTime() - new Date(a.lastActiveAt).getTime();
    });
}, [rawConversations, searchQuery]);
```

**原则**

- Zustand selector 中**只能返回**：原始值（string / number / boolean）、对象引用（需确保引用稳定）、函数引用（store 方法在创建时固化，引用稳定）
- 需要计算的派生值用 `useMemo` 在组件内处理
- 不要在 selector 中调用会产生新引用的函数

### 架构决策

- **contentEditable 替代 textarea + 覆盖层**：覆盖层方案中 `color: transparent` 导致文字不可见、div 与 textarea 换行对齐永远不同步。contentEditable 原生支持 inline chip（`contentEditable="false"` 的 span），浏览器处理光标/换行/删除，代价是 DOM 操作直接绕过 React、需手动处理 selection 和 mention 检测时序
- **mention 解析从正则改为字面量匹配**：`@(\S+?)` 无法匹配带空格的 Agent 名（如 Claude Code），改为按名称长度降序遍历 `@Name` 字面量，避免短名误匹配长名
- **暂不回退到纯 textarea**：contentEditable 的已知 bug（群聊偶发失效）不足以否定 chip 体验，后续可针对性修
